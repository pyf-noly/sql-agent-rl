# P5 结果记录：outcome-only GRPO 到底能不能训起来

> 环境：AutoDL 单卡 RTX 4090 24G · 2026-11-04 晚 · 约 4.5 小时 GPU / ¥9
> 模型：Qwen3-4B-Instruct-2507 + LoRA(r=16) · 数据 Spider 1.0
> 代码：`training/train_grpo.py`（自研轻量 GRPO，1 个 inner epoch，ratio≡1）

---

## 1. 目标

在 P4 的 SFT（dev300：单轮 78.0% / 三轮 87.0%）之上，用 **outcome-only GRPO**
拿到"RL 比 SFT 好"的第一个证据，并逐层排查"训不起来"的原因。

## 2. 四次尝试：零方差是主旋律

GRPO 的优势是组内相对的：一组全对或全错 → 标准差 0 → 优势 0 → 该步对梯度零贡献。
所以第一个要测的指标就是 `zero_var_ratio`。

| # | 设置 | 有梯度步数 | 结论 |
|---|---|---|---|
| 1 | 三轮，全量 1500 prompt，G=4 | **10%** | 任务饱和：reward 0.95 |
| 2 | 三轮，hard/extra 396，加轮级塑形（每多一轮 −0.1） | **26%** | 塑形有效但不够 |
| 3 | 三轮，**库级留出** 342 条，G=4 | 12%（p 均值 0.90） | 换数据没用：三轮口径本身就太容易 |
| 4 | 单轮，库级留出，T=1.0 | 13~19% | 换采样参数也只到 19% |

**逐层排除的诊断链**：

1. **不是实现 bug**：`mask_mismatch` 恒 0、`ratio_mean` 恒 1.0、显存正常；
2. **不完全是"题太简单"**：hard/extra 的 p 也只有 0.86；
3. **不是"训练库被背下来了"**：换成 30 个留出库后单轮仍只有 13~19% 有梯度；
4. **不是采样太保守**：T 从 0.9 提到 1.0、top_p 从 0.95 提到 1.0，只从 9% 提到 19%。

**真正的机制**：对同一道题，4 条轨迹的"答对/答错"几乎完全一致——
模型要么稳定会做，要么稳定不会做。**每题的成败近似确定性**，所以组内比较拿不到信号。

## 3. 最终实验：库级切分 + 单轮 GRPO

既然三轮口径饱和、采样也救不了，就把问题收敛到最干净的形式：

- **库级切分**（`scripts/make_db_split.py`）：140 个训练库里留出 **30 个**给 RL，
  SFT 只在剩下 110 个库上重训 → SFT 数据从 2369 降到 1714 条；
- RL prompt 只取这 30 个留出库的 **342 条**（对模型是"新库"难度）；
- **单轮**（max_turns=1）：避免三轮自带的三次机会把难度抹平；
- 超参：G=4、lr 5e-6、T=1.0、top_p=1.0、KL=0（见下面的"坑"）、150 步。

### 结果（dev300，20 个从未参与训练的库）

| 设置 | t1 EA | t3 EA | 执行失败 |
|---|---|---|---|
| SFT（140 库，P4） | 78.00% | 87.00% | 19/15 |
| **SFT（110 库，留出 30）** | **75.33%** | **83.67%** | 21 |
| GRPO seed 7 | **78.33%** | **85.33%** | 22/16 |
| GRPO seed 8 | **76.33%** | — | 23 |
| **相对 SFT-110 增益** | **+3.00 / +1.00（均值 +2.00pp）** | **+1.66pp** | — |

分难度（seed 7）：easy 88 / medium 83 / hard 72 / extra 51（SFT-110：84 / 80 / 71 / 49）。

### 怎么解读

- **方向一致**：两个 seed 都为正，且 **t1 与 t3 同时提升**——不是某一类题的偶然波动；
- **幅度有限**：均值 +2.0pp，n=300 时标准误约 2.4pp，**未达统计显著**（约 0.8σ），
  只能说"有正向趋势，需要更多 seed 才能定论"；
- **增益来自哪里（重要）**：分难度看，easy **+4.1**、medium **+3.0**，而 hard **+1.7**、
  extra **+2.7**。也就是说 GRPO 主要是在**补回"少 30 个库"损失的通用能力**，
  而不是学会了新的难推理。这与"训练 reward 持平（0.812→0.800）"吻合：
  模型不是把那 342 道训练题刷得更好，而是整体写作习惯更稳了一点；
- **补回了数据损失**：SFT-110 比 SFT-140 低 2.67pp，GRPO 之后 t1（78.33）反超 140 库版本（78.00）。

### 3.5 两个被数据否掉的补救方案（P7 会话考古补记）

这两条当时只写在会话里，没进报告；它们解释了"为什么最后不调参、直接换数据"：

| 尝试 | 结果 | 结论 |
|---|---|---|
| **pass-rate 校准**（只留 `0.2 < p < 0.8`） | 校准 40 条：p 均值 **0.90**、35 条全对、3 条全错，**只有 2 条（5%）**落在区间内；按 G=4 估算零方差 **0.96**，筛选后训练集只剩 **2 条** | 样本量不够开训，这条路被数据量堵死 |
| **轮级塑形**（每多一轮 −0.1） | `reward_mean` 稳定 0.802，但平均轮数 **1.65 → 1.85** | 正确率值 1、轮数只罚 0.1，模型学会"用更多轮换更多的对"——塑形被主奖励买走 |

> 证据强度：中。数据来自当时 `runs/p5_dense_he/metrics.jsonl` 的统计；
> 实例已释放、产物未入库，故只作定性记录，不进主表。

## 4. 工程上的三个坑（都会静默毁掉实验）

| 坑 | 症状 | 修法 |
|---|---|---|
| **KL 的参考策略是基座，不是 SFT** | `kl` 高达 1.7~2.6，每步把模型往"未 SFT"拉 | `kl_beta=0`；若要锚点，需另存冻结的 SFT adapter |
| `use_cache=False` 被 rollout 继承 | 生成慢 5 倍、显存暴涨、OOM | `generate_text` 显式 `use_cache=True` |
| 更新时停在 `eval()` | 梯度检查点不生效 → 4B×G 直接 OOM | `model.train()`；检查点必须在 peft 包装**前**开在基座上 |

## 5. 结论

1. **能训起来，但信号极弱**：Spider 对 4B-SFT 已接近饱和，四次尝试的零方差比例
   最低只到 74%（即 26% 有梯度）；
2. **单轮 + 库级切分是目前唯一能出正结果的口径**：+2.0pp（2 seeds，不显著）；
3. **要继续做，必须换数据而不是调参**：零方差的根因是"每题成败近乎确定"，
   而不是奖励函数或学习率。BIRD（库更大、SQL 更复杂、4B 基线 10~30%）才是
   RL 该待的地方；
4. **P6 的动机因此更强**：在信号稀疏的情况下，把"哪一轮变好"作为额外信号，
   等价于在同样样本里榨出更多梯度——这正是轮级信用分配要解决的问题。

## 6. 复现

```bash
python scripts/make_db_split.py                       # 库级切分（30 留出）
python -m training.train_sft --config configs/train/sft_db110.json
python -m training.train_grpo --config configs/train/grpo_p5_single.json \
    --init-adapter runs/sft_db110/adapter --model /root/autodl-tmp/qwen3-4b
python scripts/run_baseline.py --backend hf --turns 1 \
    --adapter runs/p5_single/adapter --model-path /root/autodl-tmp/qwen3-4b --tag p5single_t1
python scripts/compare_results.py results/baseline_*.json
```
