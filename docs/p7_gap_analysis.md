## 3. 没记录、值得补的

### 3.1 简历层（已补进 `resume_bullets.md`）

**① 有效样本率 13~19% → 38.5%。**
原计划的简历第三行本来就要写"有效样本率 __% → __%"（`agentic-rl项目执行计划.md` §7），
但我们之前只写了"零方差 0.615"，没把**翻倍**这个结果写出来。这是"换数据"这个决策最硬的收益。

**② 库级切分 = 未见库泛化协议。**
BIRD 是 **54 库 SFT / 15 库 RL / 11 库 dev，三者零重叠**；Spider 是 30 个留出库。
原计划的 E6「泛化到未见库」其实**已经内置在评测协议里**，但简历里只字未提——
面试官问"你怎么保证不是背库"时，这是最直接的回答。

**③ 成本与工期：4 天、单卡 4090、≈¥55。**
原计划估的是"7 周、90~110 小时、¥1500 预算"。实际执行是 4 个自然日、单卡、约 ¥55。
对日常实习简历来说，这是"能在小算力下闭环"的信号，不是缺点。

**④ 跨数据集迁移消融：Spider-SFT → BIRD 只 +1.4pp（n=74），所以从零 SFT。**
这是一次**被实验否掉的设计选择**，它让"BIRD 从零训"看起来有依据，而不是拍脑袋。
（已补进 README §2.2 与技术报告 §3.3。）

### 3.2 报告层（已补进 `technical_report.md` / `p5_results.md`）

**⑤ pass-rate 校准筛完只剩 2 条。**
P5 试过"只留 0.2<p<0.8"。原始输出是：**校准 40 条，p 均值 0.90（中位数 1.00），
35 条全对、3 条全错，只有 2 条（5%）落在有信号区间**；按 G=4 估算零方差 **0.96**，
筛选后的训练集只剩 **2 条**（hard 1 / extra 1）。
这解释了为什么最后放弃校准、改用"库级留出 + 单轮"——**校准这条路本身就被数据量堵死了**。
（证据强度：中。会话里有完整运行输出，但 `rl_p5_train.jsonl` 在已释放的北京实例上，未留存。）

**⑥ 轮级塑形没有降低轮数，反而升高：1.65 → 1.85。**
加"每多一轮 −0.1"的塑形后，100 步里 reward 稳定在 0.802，但平均轮数从 1.65 升到 1.85。
机制解释：正确率值 1、轮数惩罚太小，模型学会"用更多轮换更多的对"。
这是 **reward shaping 被正确率买走** 的具体例子，比"零方差 26%"更有解释力。
（证据强度：中。来自当时 `runs/p5_dense_he/metrics.jsonl` 的统计，产物未留存。）

**⑦ 训练"没在学"的两个直接指标：`grad_norm` 均值 0.185；`reward_mean` 0.812 → 0.800。**
P5 单轮 150 步：有方差 29/150（19%）、grad_norm 0.185、reward 前后段 0.812 → 0.800。
比"零方差 26%"更能说明"这不是超参问题"。
（证据强度：中，同上。）

**⑧ 工程坑两条：`nohup` 的块缓冲、`fill_turn_advantages` 忘 import。**
前者让"日志看起来卡住了"（真实进度看 `metrics.jsonl`），后者是 P6 第一次跑轮级优势时的
ImportError——本地单测只测了 numpy 部分，测不到训练脚本的 import。

## 6. 一句话结论

**三个会话里没有"漏掉的重要实验"——所有跑过的实验都有数字；漏的是"把数字翻译成简历语言"
的那一步。** 具体就是：有效样本率翻倍没写、未见库协议没写、成本工期没写、
迁移消融没写。补上这四条之后，"原计划的简历三行"与"实际做过的事"基本对齐了，
剩下的差距（≥8~10pp、≥3 seed）是**样本量与算力**的差距，不是记录遗漏——
这一点在 README §8 与技术报告 §8 里已经如实写明。
