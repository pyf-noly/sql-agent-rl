## 0. 先记住这 5 句话

1. **让一个 4B 小模型做「写 SQL → 运行 → 看报错 → 改 SQL」，最多改 3 轮。**
2. **用强化学习（GRPO）训它，不是只让它模仿标准答案。**
3. **核心创新：把奖励分到「每一轮」，而不是整条对话给一个分。**
4. **最大发现：模型改不对，不是因为训练不够，而是因为反馈里没有信息；
   加上「值检查」之后，能被救回的错题翻倍。**
5. **结论诚实：方向对、机制清楚，但样本小，没有达到统计显著。**

如果你只能记一句话：
> 我搭了一个能自动判对错的 SQL 多轮环境，用它训练 4B 模型自我纠错，
> 并研究了「一轮就做对」和「三轮才改对」该怎么分配奖励。

## 1. 背景：什么是 Text-to-SQL

**Text-to-SQL = 把一句人话翻译成 SQL 查询。**

```
输入：
  数据库结构：CREATE TABLE employee (emp_id INTEGER, emp_name TEXT, dept_id INTEGER, salary REAL)
              CREATE TABLE department (dept_id INTEGER, dept_name TEXT)
  问题：    "工程部有多少人？"

输出：
  SELECT COUNT(*) FROM employee e JOIN department d ON e.dept_id = d.dept_id
  WHERE d.dept_name = 'Engineering';
```

为什么难？因为一句话可以有很多种理解：

- 列名猜错（`emp_nme` 还是 `emp_name`？）
- join 错表 / 错字段
- 聚合口径错（`COUNT(*)` 还是 `COUNT(DISTINCT emp_id)`？）
- 大小写、空格、引号（BIRD 里有 `Free Meal Count (K-12)` 这种列名）

**两个常用数据集**：

| 数据集 | 规模 | 难度 | 我们怎么用 |
|---|---|---|---|
| Spider 1.0 | dev 1034 条 / 20 库 | 对 4B 偏简单 | P2~P5 的主实验 |
| BIRD | dev 1534 条 / 11 库 | 更难、库更大 | P6~P7 的主实验 |

**评测指标 EA（Execution Accuracy，执行准确率）**：
不看 SQL 写得像不像，而是**把 SQL 拿到数据库里跑，看结果和标准答案的结果是否一致**。
一致就算对。这是这个项目最重要的一个设计——**对错可以自动判定，不需要人来打分**。

> 为什么这点重要？因为强化学习需要「奖励」。如果奖励要靠人打分（或另一个大模型打分），
> 成本高、还会被钻空子。而 SQL 执行结果是确定的：对就是对，错就是错。这叫**可验证奖励**。

## 2. 为什么要「多轮」

模型一次写对很难。人写 SQL 也会报错，报错之后会改。所以我们也让模型改：

```
第 1 轮：模型写 SQL
       ↓ 拿到沙箱里执行
       ↓ 执行失败/成功
第 2 轮：把执行结果（报错信息）作为反馈，让模型重写
       ↓
第 3 轮：还没对就再改一次
```

这整个「模型 + 工具 + 循环」的东西，就叫 **Agent（智能体）**。
它和我们平时用 ChatGPT 的区别是：**模型不只是生成文本，它还会调用工具、看到工具的结果、再决定下一步。**

举个真实例子（BIRD 的书名拼写错误）：

```
第 1 轮：
  SELECT ... WHERE "VitalRegistrationComplete" = 'Yse'
  → 执行成功，但 0 行（值拼错了，库里其实是 'Yes'）

反馈（我们环境给的）：
  Value check: `Yse` is not found in column `VitalRegistrationComplete`.
  Closest existing values: 'Yes'

第 2 轮：模型把 'Yse' 改成 'Yes' → 执行结果和标准答案一致 → 判对
```

**这里有一个关键问题**：第 1 轮错了、第 2 轮改对，这个「功劳」应该记给谁？
这就是本项目的核心：**信用分配（credit assignment）**。

## 3. 为什么用强化学习，而不是只做 SFT

### 3.1 两种训练方式，用「考试」打比方

| | SFT（监督微调） | RL（强化学习） |
|---|---|---|
| 像什么 | 老师给你标准答案，你照着背 | 给你题，你自己做，对了加分、错了扣分 |
| 数据 | 「问题 → 标准 SQL」 | 「问题」+ 一个能判对错的裁判 |
| 学到什么 | 模仿标准答案的写法 | 自己探索出「怎样更容易做对」 |
| 缺点 | 没见过的情况就不会 | 训练不稳定、需要大量采样 |

实际做法是**先 SFT 再 RL**：先让模型学会「SQL 长什么样」（冷启动），
再让它自己试错、往「更容易做对」的方向调。

### 3.2 RL 的基本循环（用大白话）

```
1. 拿一道题
2. 让模型采样 G 条不同的尝试（我们 G = 4）
3. 每条拿去执行，判对错（奖励 1 或 0）
4. 比较这 4 条：比平均好的加分，比平均差的减分 → 得到「优势 A」
5. 用 A 去调整模型参数：让「好的尝试」更容易发生
6. 换下一道题，重复
```

第 4 步的「比较」就是 **GRPO** 这个算法的核心思想：
**不看绝对分数，看组内相对好坏。** 这样就不需要额外训练一个「价值模型」来预估分数
（PPO 需要，成本高）。这就是我们选 GRPO 而不是 PPO 的原因。

### 3.3 两个必须知道的概念

**① 零方差（zero variance）**
如果一组 4 条尝试**全对**或**全错**，那它们之间没有「相对好坏」——优势全是 0，
这一步对模型没有任何学习信号。我们把这个比例叫 `zero_var_ratio`。

- Spider 上：0.74~0.90（太简单，几乎全对）
- BIRD 上：0.615（有 38.5% 的步能学到东西）

**这是本项目第一个重要发现：任务太难或太简单，RL 都学不到东西。**

**② 优势（advantage）**
每条尝试的「相对好坏」：

```
A_i = (r_i - 组内平均) / 组内标准差
```

`r_i` 是第 i 条尝试的奖励（0 或 1）。全对的一组，A 全是 0；有对有错的一组，对的是正、错的是负。

## 4. 这个项目的四个零件

整个仓库可以拆成四块，对应四个阶段：

```
envs/      环境：执行 SQL、判错、生成反馈      （P1）
rollout/   交互与评测：模型怎么跑一轮/三轮、怎么算分（P2）
data/      数据：SFT 训练集、RL 题目、多轮修复轨迹（P3）
training/  训练：SFT 和 GRPO 的实现            （P4~P6）
```

### 4.1 环境（`envs/`）：为什么它值得认真做

环境是模型的「工具」。它必须做到三件事：**安全、确定、能给出有用的反馈**。

**安全**（模型可能写出危险 SQL）：

| 防线 | 做法 | 为什么 |
|---|---|---|
| 只读 | 用 `mode=ro` 打开数据库 | 数据库自己拒绝写操作，不依赖我们的代码 |
| 只允许查询 | 只放行 `SELECT` / `WITH` | 防止 `DROP TABLE` |
| 单语句 | 检测到多条语句就拒绝 | 防止 `SELECT 1; DROP TABLE x` |
| 超时 | 2 秒（评测时 10 秒） | 防止死循环查询把机器挂死 |
| 结果截断 | 最多返回 N 行 | 防止查出 100 万行把内存打爆 |

**反馈**（模型改错的依据）：

我们把数据库报错分成 9 类，每类给不同的提示。比如：

- 列名不存在 → 告诉它**这张表真实有哪些列**
- 表名不存在 → 告诉它**库里有哪些表**
- 列名歧义 → 告诉它**这列在哪几张表里都有，请加表名限定**
- 超时 → 提示「可能是漏了 join 条件」
- 执行成功但 0 行 → 提示「检查 WHERE 里的值和 join 键」

**关键纪律：反馈里绝对不能出现标准答案。** 否则模型等于开卷考试，指标会虚高，
而且线上根本没有标准答案可看。仓库里有一个专门的测试钉死这一条。

**值检查（P6 加的）**：
执行成功时，额外查一句「你 WHERE 里的这个字符串，库里真的有吗？」
没有的话，告诉它「这个值不存在，最接近的是 'Yes'」。
这是「环境看得见、模型看不见」的合法信息——它不说答案，只说「你写的这个东西库里没有」。

### 4.2 数据（`data/`）：最费脑子的部分

**SFT 需要什么？** 「问题 + 标准 SQL」，再加上 system prompt、数据库结构、反馈外壳。
Spider 有 2574 条。

**多轮数据从哪来？** 这是 P6 最麻烦的地方。我们需要「错误 SQL → 反馈 → 正确 SQL」的轨迹，
但标准数据集里只有正确答案。我们试了三条路：

| 方案 | 做法 | 成功率 | 结论 |
|---|---|---|---|
| ① 让强模型（DeepSeek）直接做 3 轮 | 它第一轮就全对了 | 3/3 全对 | 没有修复轨迹可学 |
| ② 让强模型改 4B 的真实错误 | 4B 先错 → 给反馈 → DeepSeek 改 | **10%** | 不可用 |
| ③ **自己造「可检测的错误」** | 把标准答案里的列名换成本库另一张表的真实列 → 数据库真报错 → 目标是原答案 | **94%** | 采用 |
| ④ 造「取值错误」 | 把 `Yes` 改成 `Yse` → 值检查提示 → 目标是原答案 | **99%** | 采用 |

方案②失败的原因，是整个项目**最重要的一条观察**：

> 4B 的错题里，**79%~90% 是「执行成功但结果错」**（join 错字段、聚合写错）。
> 这类错误，执行反馈只会说一句「Execution succeeded: 1 row」——**没有任何可用的纠错信息**。
> 连 DeepSeek 看了都改不对，成功率只有 10%。

**这一步直接推导出了项目的核心结论**：自修复的上限，由**反馈的信息量**决定，而不是由训练步数决定。

最终数据（`data/bird_p6/`）：

```
1990 条单轮 gold
1133 条多轮·schema 修复（列名不存在）
 795 条多轮·取值修复（值不存在）
= 3918 条，多轮占 49%
```

**一个容易踩的坑**：多轮样本里，「故意写错的第一轮」不能算进训练目标（loss），
否则模型会学成「先随手写一个，等反馈再改」。我们一开始就踩了这个坑，单轮准确率掉了 4.6pp
（51.47% → 46.91%）。修正方法是给样本加一个标记，只对**最后一轮（改正后的 SQL）**算 loss。

### 4.3 训练（`training/`）：LoRA 和 GRPO

**LoRA 是什么？**
4B 模型有 40 亿参数，全量微调要几十 GB 显存。LoRA 不改原参数，只在旁边加一小块
「低秩矩阵」，只训练这一小块（本项目 33M 参数，占 0.81%）。
效果接近全量微调，显存只要 12GB 左右——一张 4090 消费级显卡就够。

**SFT 做了什么？**

- 2 个 epoch，max_len 2560，学习率 2e-4
- 关键细节：**训练时的文本序列，必须和推理时逐字一致**。
  我们直接在 rollout 时保存「真正发给模型的消息」，训练时原样重建，
  避免「训练模板」和「推理模板」悄悄不一样（这种 bug 不报错，只会让效果变差）。

**GRPO 做了什么？**

- 每道题采样 4 条，比较相对好坏
- KL 惩罚设为 0（原因见 §7 的坑）
- 1 个 inner epoch（同一批数据只更新一次，所以 `ratio` 恒等于 1）

**轮级优势（本项目的创新点）**：
普通 GRPO 给整条轨迹一个优势。我们的做法是：

```
y[i,t] = 1     如果第 i 条轨迹「第一次做对」发生在第 t 轮（否则 0）
A_turn[i,t] = (y[:,t] - 平均) / 标准差      ← 每一轮单独在组内比较
A[i,t] = A_episode[i] + β · A_turn[i,t]     ← 加起来
loss = -min(ratio·A, clip(ratio)·A)          ← 用逐 token 的优势算 loss
```

三个设计决定，面试会被问：

1. **β=0 时严格退化成普通 GRPO**：所以「轮级 vs 普通」的对比不需要写第二套代码；
2. **某一轮组内全同 → 优势置 0**：没方差就不给梯度，不让浮点噪声变成信号；
3. **它只能救「全对组」**：全错组里 y 全是 0，轮级优势也救不了——这是它的理论上限。

### 4.4 评测（`rollout/`）：数字是怎么算出来的

**一次评测 = 对每道题跑一遍 Agent，然后用 EA 判对错，最后统计。**

三个容易混淆的点：

1. **单轮 vs 三轮**：
   - 单轮（t1）= 只给一次机会
   - 三轮（t3）= 判对才停，最多 3 次。测的是「多轮修复的上限」
   - 注意：不能用「执行成功就停」，否则三轮会退化成单轮（因为大部分 SQL 都能执行）
2. **两种口径**：
   - `rows`：行数一致 + 排序后比较 + 数值归一化（宽松，Spider 历史口径）
   - `bird`：官方口径，原始元组、列顺序敏感（严格，和论文比用这个）
   - 同一批数据，两个口径差 3.7pp，所以必须写清楚用的哪个
3. **抽样误差**：
   - 307 条抽样的标准误约 2.9pp；1534 条全量约 1.3pp
   - 我们最后补了全量：**50.85%**（307 条抽样是 51.79%，偏乐观 0.94pp）

## 5. 结果怎么读（每一行都讲清楚）

### 5.1 Spider（P2~P5）

| 设置 | 单轮 | 三轮 | 说明 |
|---|---|---|---|
| DeepSeek（大模型 API） | 84.33% | 89.00% | 对照，不是我们要训的模型 |
| 4B + SFT | 78.00% | 87.00% | 第一次真训练；三轮比单轮 +9pp |
| 4B + SFT（少 30 个库） | 75.33% | 83.67% | 留出 30 个库给 RL，数据变少的代价 |
| + GRPO（两个随机种子） | 78.33 / 76.33 | 85.33 / — | 均值 +2.00pp，但没到显著 |

**读到什么**：
- 4B 比 DeepSeek 低 6pp，但**多轮增益更大**（+9 vs +4.7）——因为它的错更多是
  「聚合口径/JOIN」这类反馈能定位的问题；
- GRPO 只涨 2pp，而且训练时 **90% 的组零方差**——任务对 4B 太简单了。
  这就是为什么后来换 BIRD。

### 5.2 BIRD（P6，同一批 307 条）

| 设置 | 单轮 | 三轮 | 多轮才救回 |
|---|---|---|---|
| 4B 零样本 | 49.8% | — | — |
| 单轮 SFT | 50.16% | 53.09% | 9 |
| + GRPO（200 步） | 50.16% | — | — |
| 多轮 SFT v1 | 51.47% | 54.07% | 8 |
| + GRPO outcome-only | 51.14% | — | — |
| **+ GRPO 轮级优势** | **52.77%** | **56.03%** | 10 |
| 多轮 SFT v2（未 mask） | 46.91% | 55.37% | 26 |
| **多轮 SFT v3（mask 第一轮）** | **51.79%** | **57.00%** | **16** |
| **v3 全量 1534 条（单轮）** | **50.85%** | — | — |

**怎么读这一大坨**：

1. **换数据有用**：零方差从 0.90 降到 0.615，有梯度的步数从 13~19% 提到 38.5%；
2. **但普通 GRPO 还是没用**：200 步，50.16% → 50.16%，一点没动；
3. **轮级优势是唯一超过 SFT 的**：52.77% vs 51.14%（+1.63pp），hard 档 +4.3pp；
4. **多轮修数据要 mask**：v2 修复率 8.5% 但单轮掉 4.6pp；v3 mask 后单轮回来、三轮最高；
5. **全量 50.85%**：307 条抽样偏乐观 0.94pp，所以主数字要用全量。

### 5.3 为什么说「不显著」

这是最容易被面试官抓的点，必须理解。

- 我们在**同一批 307 条题**上比较两个模型，所以要用**配对检验**（McNemar）：
  只看「一个对一个错」的样本，而不是把两组当独立样本；
- v3 三轮 vs v1 三轮：+2.93pp，不一致对 31/22，**p = 0.272**；
- 轮级 vs outcome-only：+1.63pp，**p = 0.18**；
- 唯一显著的是「三轮比单轮好」：+5.21pp，**p < 0.001**。

**p 值是什么？** 假设两个模型其实一样好，那么「观察到至少这么大的差距」的概率。
p=0.27 意味着：有 27% 的概率，这个差距是抽样噪声造成的。所以不能写「显著提升」。

**要多少样本才能显著？** 按当前效应量算：
- p<0.05 约需 770 条
- 80% 功效约需 1577 条

这就是为什么我们**没有**继续烧钱做 3 个 seed——即使做了，很可能还是不显著。

## 6. 三个机制发现（面试讲这三个就够）

### 发现 1：零方差不能用平均准确率估算

我们一开始按二项分布估算：p=0.5、G=4 时，全对概率 `p⁴`、全错 `(1−p)⁴`，
加起来约 0.125。**实测是 0.615，差了 5 倍。**

原因：那个公式假设「每道题的成功率都一样」，但真实的难度是**双峰**的：
200 步里 67 步是「4 条全对」（模型已经会的题）、56 步是「4 条全错」（模型够不着的题），
可学的只有中间 77 步（38.5%）。

**教训：均值准确率不能预测信号量，必须实测。**

### 发现 2：轮级优势只在「全对组」里有用

- 「全对组」：普通 GRPO 优势全是 0，但轮级优势能区分「1 轮解出」和「3 轮才解出」；
- 「全错组」：轮级也救不了（y 全是 0）；
- 「中间组」：普通 GRPO 本来就有信号。

这解释了为什么轮级优势的增益集中在 hard（+4.3pp）——难题需要多次尝试，过程才有分化。

### 发现 3：反馈的信息量决定自修复的上限

三条独立证据：

1. BIRD 首轮错题的 **79%~90% 是「能执行但结果错」**，执行反馈看不见；
2. 让 DeepSeek 改 4B 的真实错误，成功率只有 **10%**——不是教师不行，是反馈没信息；
3. 加了「值检查」（能检测「值拼错」这一类）后，多轮才救回从 **2.6% → 5.2%**，
   三轮准确率 54.07% → **57.00%**。

**结论：RL 只能让模型更好地利用已有信息，不能凭空造出信息。**

## 7. 踩过的坑（挑 5 个能讲 20 分钟的）

| 坑 | 现象 | 为什么 | 怎么修 |
|---|---|---|---|
| KL 惩罚的参考模型选错 | `kl` 高达 1.7~2.6，越训越差 | 参考的是「没 SFT 的基座」，等于每步把模型往回拉 | `kl_beta=0` |
| 多轮数据没 mask 第一轮 | 单轮掉 4.6pp | 模型学会了「先写错等反馈」 | 只对最后一轮算 loss |
| 逐 token 优势形状错位 | `578 must match 579` | 位置 t 的 logits 预测 t+1，优势要平移一位 | `adv[:, 1:]` 对齐 |
| 结果截断造成假阳性 | 两个不同 SQL 被判「等价」 | 两边都截断到同样前缀 | `max_rows=20000` |
| `nohup` 日志「卡住」 | 训练看起来没输出 | Python 的 stdout 是块缓冲，攒够 8KB 才写 | 看 `metrics.jsonl` |

## 8. 如果面试官问……

（完整 10 问在 `docs/interview_qa.md`，这里给最常问的 4 个）

**Q：你这个项目和「我用 verl 跑通了 GRPO」有什么区别？**
A：我做的是**机制**，不是调包。我定位了多轮场景下 outcome reward 的信用分配缺口，
用零方差量化了它（0.615），实现了轮级优势，并且用 β=0 的严格退化做免费消融。
另外我没有用 verl——因为要改 advantage 的计算方式，自研 1400 行反而更省事。

**Q：+2.93pp 不显著，那这个项目有什么价值？**
A：价值在三条可复用的结论：① 零方差必须实测，均值估算会高估 5 倍；
② 轮级优势的有效范围只有「全对组」；③ 自修复的上限由反馈信息量决定（三条独立证据）。
负结果也是结果，但必须有机制归因——我给了。

**Q：为什么用 4B 这么小的模型？**
A：因为 BIRD 上 4B 零样本 49.8%，正好落在 GRPO 需要的中等难度区间；
更大的模型会直接把任务刷简单，零方差更高。结论是机制层面的，不是 SOTA 对比。

**Q：你怎么保证不是背答案 / 数据泄漏？**
A：① 库级切分：BIRD 54 个库训练 / 15 个库 RL / 11 个库评测，三者零重叠；
② 反馈里绝不出现标准答案，有专门测试；③ 评测用的 dev 库从未参与训练。

## 9. 名词表（按出现顺序）

| 名词 | 一句话解释 |
|---|---|
| LLM | 大语言模型，这里指 Qwen3-4B |
| Token | 模型处理文本的最小单位，约等于 0.7 个汉字或 0.75 个英文单词 |
| LoRA | 只训练一小块「外挂参数」的微调方法，省显存 |
| SFT | 监督微调：给「问题 + 标准答案」，让模型模仿 |
| RL | 强化学习：自己试，按结果好坏调整 |
| Rollout | 让模型实际跑一遍、产生轨迹的过程 |
| Episode / 轨迹 | 一道题从第一次尝试到停止的完整记录 |
| Turn / 轮 | 轨迹里的一次尝试 |
| Reward | 奖励，这里是「执行结果和标准答案一致 = 1，否则 0」 |
| Advantage | 优势，一条尝试相对同组其他尝试好多少 |
| GRPO | 一种 RL 算法：用组内相对好坏当优势，不需要 critic |
| KL | 衡量两个模型输出分布差异的指标，用来防止训歪 |
| Zero variance | 一组尝试全对/全错，没有学习信号 |
| EA | 执行准确率，跑出来的结果对就算对 |
| Seed | 随机种子，换一个种子重跑就是一次独立性检验 |
| p 值 | 「如果两个模型一样好，出现这么大差距的概率」 |
| 置信区间（CI） | 真值有 95% 概率落在的区间 |
| 配对检验 | 同一批题上比较两个模型，只看「一对一错」的样本 |
| 显著 | p < 0.05，通常才敢说「真的有提升」 |

## 11. 学习路径（如果要从零补基础）

1. **SQL 基础**：SELECT / JOIN / GROUP BY / 子查询（能看懂 gold SQL）
2. **Transformer / LLM 基础**：token、注意力、生成过程（知道模型在干什么就行）

## 12. 最后：怎么用这个项目讲故事

**30 秒版**：
> 我搭了一个多轮 Text-to-SQL 智能体，让 4B 模型自己写 SQL、看执行反馈、改错。
> 用 GRPO 训练时发现一个核心问题：多轮场景下，整条轨迹一个奖励分不清「一轮做对」
> 和「三轮才改对」。我实现了轮级优势来解决它，并用零方差量化了问题。
> 最大的发现是：模型改不对的根因是反馈里没有信息，而不是训练不够。

**2 分钟版**：在 30 秒版基础上，加 §5.2 的三代数据对比和 §6 的三个机制发现。

**10 分钟版**：加 §4（环境/数据/训练/评测怎么搭的）+ §7（踩过的坑）+ §5.3（为什么不显著）。

**被挑战时的保命句**：
> 所有数字都在 `results/*.json` 里，可以离线复算；不显著的地方我都写了 p 值和置信区间，
> 没有把 0.27 说成 0.05。
