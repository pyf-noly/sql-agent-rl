# P4 决策记录：为什么这样训

> 这份文件的作用：三个月后你（或面试官）问"你为什么不直接用 verl / 为什么是单步更新"，
> 这里就是答案。每个决定都写了"替代方案是什么、为什么没选"。

## 1. 训练框架：自研轻量 GRPO，而不是 verl / TRL

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| **verl**（行业主流） | 多卡、vLLM rollout、社区方案多 | 要装 Ray + vLLM + flash-attn，版本矩阵对临时租的 4090 不友好；多轮 agent 要写 `AgentLoopBase` 子类；**P6 改 advantage 时要动它的内部实现**，升级即冲突 |
| **TRL GRPOTrainer** | 单卡友好、维护活跃 | 多轮工具调用要靠 `environment_factory`，奖励函数拿到的是文本，**token 级 mask 不可控**；P6 的轮级优势接不进去 |
| **自研（本方案）** | 200 行看懂每一行；P6 直接改 advantage；无重依赖 | 慢（HF generate 比 vLLM 慢 2~4 倍）；没有多卡 |

**关键理由**：这个项目的差异化是 **P6 的轮级信用分配**，它必须改 advantage 计算。
框架越重，这个改动越痛苦；而在 4B + 单卡 + 20~300 步的规模下，vLLM 带来的加速
（约 2~4 倍）**不足以抵消集成成本**——P5 的 300 步大概 8~12 小时，¥20~30，
可以接受。

**什么时候应该换回 verl**：要上 8 卡、或步数涨到 3000+、或需要 FSDP 切分模型时。
接口已经隔离在 `training/model.py::generate_text`，换生成后端不影响训练逻辑。

## 2. 模型：Qwen3-4B-Instruct-2507 + LoRA(r=16)

- 4B 全参在 24G 上放不下（权重 8G + Adam 状态 32G + 激活）；
- LoRA r=16 可训练参数约 **40M（1%）**，显存峰值 ~16~18G，4090 刚好；
- 选 **Instruct** 而不是 base：base 模型不保证输出 ```` ```sql ```` 块，
  P4 会因为"格式全错"收到满屏 `parse_error`，把冒烟测试变成排查格式问题。

**回退方案**：如果 24G 上仍然 OOM，换 `Qwen/Qwen3-1.7B`（`--model` 覆盖），
或把 `max_len` 降到 1536。

## 3. 奖励：只用"最终 SQL 执行等价"，二分

- 奖励 = 1（执行结果与 gold 等价）/ 0（不等价），解析失败额外 -0.2；
- **不做过程奖励**：过程奖励是 P6 的实验组（C），P4/P5 必须先把 outcome-only 的
  基线跑出来，否则"提升"没有对照；
- 解析失败扣分是**唯一**的塑形：它区分"不会写 SQL"和"不会按格式输出"，
  后者是格式问题，不值得和语义错误同分。

## 4. 每个样本只更新一次（1 个 inner epoch）

标准 PPO 会在一批数据上做多个 epoch；这里只做 1 次，于是
`exp(logp_new - logp_old) ≡ 1`，裁剪分支永不触发——**这不是 bug，是 Dr.GRPO 的做法**。

- 好处：不需要重要性修正，不引入 off-policy 偏差，代码少一半；
- 代价：样本利用率低（每条轨迹只用一次）；
- 为什么 P4 可以接受：冒烟阶段要的是"信号方向对不对"，不是样本效率。

`ratio_mean` 因此被当作**一级验收指标**：它必须恒为 1.0；不是 1 就说明
"老策略 logp"用错了权重，这是 RL 里最典型的静默 bug。

## 5. 数据：SFT 重建为推理同构格式

P3 的 `sft_final.jsonl` 有两个会导致训练-推理不一致的问题（详见
`scripts/build_p4_data.py` 头部注释）：

1. 没有 system prompt / schema → 模型会学"不看表瞎编 SQL"；
2. 多轮反馈消息缺 `Your previous attempt: ...` 外壳 → 训练见到的输入
   和推理时不是同一个分布。

所以 P4 第一件事是**重建**，而不是直接开训。重建后：
`data/train/sft_train.jsonl`（2369）/ `sft_val.jsonl`（205）/ `rl_train.jsonl`（1500，含 gold）。

## 6. 算力与预算

| 项 | 配置 | 时长 | 花费 |
|---|---|---|---|
| SFT（2 epoch，2673 条 after 过采样） | 4090-24G | 30~50 min | ¥2~4 |
| 评测（dev300 × 单轮 + 三轮） | 同上 | 40~60 min | ¥3~5 |
| GRPO 冒烟（20 步 × G=4） | 同上 | 10~20 min | ¥1~2 |
| 模型下载/调试（无卡模式） | — | 1 h | ¥0.1 |
| **合计** | | **2~3 h** | **¥8~15** |

比原估的 ¥15~25 低，原因是：不上 vLLM（省安装时间）、SFT 数据短
（`context_ratio ≈ 0.3`，平均 390 token）、冒烟只跑 20 步。

## 7. 已知风险

| 风险 | 触发信号 | 预案 |
|---|---|---|
| 4B-SFT 的 EA > 75%（任务太简单） | 第 7 步的结果 | 主表只报 hard/extra；或加 CoT 提升难度 |
| 4B-SFT 的 EA < 40% | 同上 | 先看 `pred_error` 占比，区分格式问题 vs 能力问题 |
| 多轮增益 < 3pp | `t3 - t1` | P6 的假设不成立，要改任务设计或换 7B |
| GRPO reward 不涨 | 冒烟 20 步 | 查 `zero_var_ratio`、采样温度、lr；别急着加步数 |
| 模板 mismatch > 0 | `check_p4_env.py` | 停下，不要硬训（梯度是错的） |
