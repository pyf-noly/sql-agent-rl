# 技术报告：面向 Text-to-SQL 的多轮自我修复 Agent 与轮级信用分配

> 版本：v1.0（2026-11-06）· 项目周期：2026-11-03 ~ 2026-11-06
> 硬件：单卡 RTX 4090-24G（AutoDL），本地 RTX 4060-8G 做 4-bit 方向性评测
> 基座：Qwen3-4B-Instruct-2507 + LoRA(r=16, α=32)
> 数据：Spider 1.0、BIRD
> 代码：`sql-agent-rl/`（230 个单测）· 全部数字来自 `results/*.json`

---

## 摘要

本项目研究一个问题：**多轮工具调用 Agent 在只有结果奖励（outcome reward）时，
"过程"能不能被训练出来？**

做法是搭一个可验证的多轮 Text-to-SQL 环境（只读 SQLite + 结构化执行反馈），
用 4B 模型做 SFT 冷启动，再用自研 GRPO 训练；核心改动是把整条轨迹的优势拆到每一轮
（轮级信用分配），并用 **β=0 严格退化成 outcome-only** 的设计保证消融免费。

主要结论有四条：

1. **零方差是这类任务的主要瓶颈，且不能用均值准确率预测**。Spider 上实测零方差
   0.74~0.90（90% 的组没有梯度）；BIRD 上降到 0.615，有梯度的步数从 13~19% 升到 38.5%。
   按 `p⁴+(1−p)⁴` 估算 p=0.5 时零方差应为 0.125，实测 0.615——因为真实难度分布是双峰的。
2. **outcome-only GRPO 在 BIRD 上也推不动分数**（200 步，50.16% → 50.16%）。
   原因不是实现 bug（`mask_mismatch` 恒 0、`ratio_mean` 恒 1.0），而是每次更新只有
   约 308 条有效轨迹。
3. **轮级优势是本项目唯一跑赢 SFT 基线的配置**（单轮 52.77% vs outcome-only 51.14%，
   +1.63pp；hard 档 +4.3pp），但 n=307、单 seed 时配对检验 p=0.18，不显著。
4. **自修复的上限由反馈的信息量决定，而不是训练步数**。执行反馈只能发现一小部分错误：
   BIRD 首轮错题里 **79%~90% 是"跑得对但结果错"**（307 条评测 117/149，抽样 26/29），
   执行报错只占 10%~21%。加入取值存在性检查后，"多轮才救回"从 2.6% 升到 5.2%，
   三轮准确率 54.07% → **57.00%**（+2.93pp，配对 p=0.27）。而"故意写错的第一轮"
   必须 mask 掉，否则单轮会掉 4.6pp。**全量 1534 条单轮 50.85%（±1.3pp）**，
   v3 的单轮没有再牺牲。

一句话：**机制都验证了（能跑、方向对、可解释），但在这套数据与这个样本量上，
收益只有 1~3pp 量级，且未达统计显著。** 本报告如实报告这一点。

## 1. 问题定义

### 1.1 任务与环境

输入：数据库 schema（DDL）+ 自然语言问题（BIRD 还带 evidence）。
输出：一条 SQLite 查询。执行后把结果或报错回灌，最多 3 轮。
奖励：执行结果与 gold 结果等价（0/1），无过程塑形。

### 1.2 信用分配的缺口

GRPO 用组内相对奖励当优势：

```
A_i = (r_i - mean(r)) / (std(r) + eps)
loss = -mean(min(ratio·A_i, clip(ratio)·A_i))
```

一条轨迹的所有 token 共享 `A_i`。在多轮场景下这有两个问题：

1. **组内全对时优势全 0**——"一轮解出"和"三轮才解出"拿一样的分数，最该学的过程被浪费；
2. **无法区分"改对了"和"瞎改"**——P3 的失败分析显示 82% 的失败轨迹里模型**确实改了 SQL**
   但三轮仍错，说明它缺的不是"产生变化"，而是"变化的方向"。

### 1.3 本报告要回答的三个问题

- Q1：任务难度是否给了 RL 足够的梯度信号？（P4/P5/P6）
- Q2：轮级信用分配能不能把"过程"变成可学的信号？（P6）
- Q3：多轮自修复的能力瓶颈在哪？（P3/P6）

## 2. 环境

### 2.1 只读沙箱

| 防线 | 实现 | 为什么 |
|---|---|---|
| 物理只读 | `sqlite3.connect("file:...?mode=ro", uri=True)` | 不依赖自己的解析代码，SQLite 内核强制 |
| 单语句 | `sqlite3.complete_statement` + `sqlparse.split` 双层 | 前者管"完不完整"，后者管"几条语句" |
| 白名单 | 首关键字 `SELECT`/`WITH` + 写操作关键字黑名单 | CTE 的 `get_type()` 是 `UNKNOWN`，不能拿它当主判据 |
| 软超时 | `set_progress_handler(guard, 2000)`，每 2000 条 VM 指令查一次 deadline | 协作式中断，返回结构化 `timeout`，不杀进程 |
| 截断检测 | `fetchmany(max_rows + 1)` | 多取一行才能区分"刚好 max_rows"和"被截断" |

**结果截断的隐藏后果**：BIRD 有 55 条 gold 结果超过 1000 行。若沿用 1000 行上限，
两条不同的 SQL 会被截成相同前缀而判"等价"——这是假阳性，比假阴性更危险。
所以 BIRD 评测固定 `--max-rows 20000 --timeout 10`。

### 2.2 错误分类与反馈

9 类错误：`invalid_sql`（沙箱拒绝）/ `syntax` / `no_such_column` / `no_such_table` /
`ambiguous_column` / `timeout` / `empty_result` / `db_error` / `unknown`。

反馈文本单独成文件（`envs/feedback.py`），是环境到模型的唯一文字接口：

- schema 类错误附**真实列名/表名**（`include_schema_hint` 可关，供 P6 消融）；
- 行注释结尾需要补 `\n;` 才能通过 `complete_statement`，否则合法查询会被误杀；
- 反馈里**绝不能出现 gold SQL 或正确答案**，有专门的 3 组参数化测试钉死。

### 2.3 值检查（P6 新增）

执行成功时，额外检查 `WHERE` 里的字符串字面量是否真的存在于库中：

```
Value check: a literal in your query does not exist in the database.
- `Yse` is not found in column `VitalRegistrationComplete`. Closest existing values: 'Yes'
```

做法：从 SQL 抽 `col = 'lit'` / `col IN (...)` / `col LIKE '...'`，跨"所有含该列的表"
用参数化查询确认存在性（2s 预算），不存在时用 difflib 给最近的真实取值。

**为什么这样做而不是给正确答案**：它只回答"这个值库里没有"，不回答"应该填什么"。
它把"跑得对但结果错"里的一类（值拼错）变成了可检测信号，属于环境合法可见的信息。

### 2.4 环境可信度的验证

| 检查 | 结果 |
|---|---|
| gold-as-gold（Spider dev 全量 1034 条） | **100.00%**（0 失败） |
| 单测 | **230 passed**（沙箱 40、错误分类 29、评测 25、其余按模块） |
| 注入攻击测试 | `SELECT 1; DROP TABLE x` 被 `multi_statement` 拒绝；`DROP/UPDATE/ATTACH` 全部拒绝 |
| 训练/推理由同一套 messages 构造 | `chatfmt` 用模板长度相减对齐 mask，`n_mismatch` 恒 0 |

### 3.1 Spider（P2~P5）

- dev300 分层抽样（seed 42）：easy 73 / medium 132 / hard 58 / extra 37，20 个库；
- train 140 库：SFT 2574 条（多轮 194 条，5.4%，过采样 3~5 倍）；
- P5 的库级切分：留出 30 个库给 RL，SFT 只用 110 库的 1714 条，RL prompt 342 条。

### 3.2 BIRD（P6）

| 项 | 值 |
|---|---|
| dev | 1534 题 / 11 库 / 1.71GB；easy 925 / medium 464 / hard 145；1386 条带 evidence |
| train | 9428 题 / 69 库 / 30.18GB（压缩包 8.92GB，内含第二层 zip） |
| 库级切分 | **54 库 SFT / 15 库 RL / 11 库 dev**，三者零重叠 |
| SFT / RL / val | 3920 / 1976 / 80 条 |
| prompt 长度 | dev p95 ≈1865 tokens；SFT tokenize 后 p95 1630 / max 2098 |
| 评测抽样 | dev 等距 **stride 5 → 307 条**（dev.json 按库排序，直接 limit 只会测前几个库） |

**一条被实验否掉的捷径**：把 Spider-SFT 的 adapter 直接迁到 BIRD，零样本 40.9%（bird 口径），
与 base 的同题配对只 **+1.4pp（n=74）**——等于没有迁移。所以 BIRD 从零 SFT，
不做"Spider → BIRD"两阶段。

### 3.3 多轮修复轨迹的合成

P6 需要"错误 → 反馈 → 改正"的轨迹，试过三条路：

| 方案 | 做法 | 成功率 | 结论 |
|---|---|---|---|
| ① 强模型直接做 3 轮 | DeepSeek 跑"判对才停" | 首轮 3/3 全对 | 没有修复轨迹 |
| ② 强模型改 4B 的真实错误 | 4B 先试 → 反馈 → DeepSeek 改 | **10%**（只留可检测错误也仅 29%） | 不可用 |
| ③ 构造 schema 错误 | gold 列名换成本库另一表的真实列 → 真报 `no such column` | **94%**（1133/1200） | 采用 |
| ④ 构造取值错误 | gold 里的真实值改坏（`Yes`→`Yse`）→ 值检查提示 | **99%**（788/795） | 采用 |

②失败的原因是全项目最重要的一条观测：**4B 的首轮错题里 79%~90% 是"执行成功但结果错"**
（join 错字段、聚合写错；BIRD 307 条评测 117/149，抽样 26/29），反馈只有
`Execution succeeded: 1 row`——教师没有任何依据去改，强行教只会学到瞎猜。

最终数据（`data/bird_p6/`）：

| 类型 | 条数 |
|---|---|
| 单轮 gold | 1990 |
| 多轮·schema 修复（列名不存在） | 1133 |
| 多轮·取值修复（值不存在） | 795 |
| 合计 | **3918**（多轮占 49%） |

修复样本带 `meta.mask_first_turn=True`：SFT **只对最后一轮（改正后的 SQL）算 loss**。
这一条是 v3 的关键（见 §6.4）。

## 4. 方法

### 4.1 SFT 冷启动

- LoRA r=16 / α=32，2 epoch，max_len 2560，batch 2 × grad_accum 8，lr 2e-4，bf16 + 梯度检查点；
- 训练序列与推理**逐字一致**：由 `rollout/agent.py` 里保存的 `Turn.feedback_message`
  原样重建，而不是训练时再拼一遍模板——两套模板会静默分叉；
- mask 只在助手 token 上为 1，反馈 token 为 0。

### 4.2 outcome-only GRPO

自研轻量实现（`training/`，约 1400 行）：

| 项 | 选择 | 理由 |
|---|---|---|
| 算法 | GRPO，G=4，1 个 inner epoch | ratio ≡ 1，更新简单，省一个 critic |
| KL | **β=0** | 参考策略是基座而非 SFT，KL=1.7 会把模型拉回未 SFT 状态 |
| 采样 | T=1.0，top_p=1.0 | 降温度只会让零方差更严重 |
| 长度 | max_len 2560，max_new_tokens 256 | 多轮样本 3072 会 OOM（reserved 6.5G 碎片） |
| 奖励 | 对 1，错 0，解析失败 −0.2 | 无过程塑形（P5 试过，不够） |

### 4.3 轮级优势

```
y[i,t] = 1                      当且仅当轨迹 i 第一次做对发生在第 t 轮（没做对则全 0）
A_turn[i,t] = (y[:,t] - mean_t) / std_t · γ^(t-1)     逐轮次在组内标准化
A[i,t] = A_ep[i] + β · A_turn[i,t]
loss = -min(ratio·A, clip(ratio)·A)                    token 级，按轮铺开
```

三个设计决定：

1. **β=0 严格退化成 outcome-only**：消融对照不需要第二份代码；
2. **组内该轮全同 → 置 0**：坚持"没方差就不给梯度"，不给浮点噪声放行；
3. **轮级只做加法**：真正的更新量是 `A_ep + β·A_turn`，全错组仍然为 0
   （轮级救不了全错）。

实现细节：`advantages` 支持 `[B]` 与 `[B, L]` 两种形状；后者取 `adv[:, 1:]` 与
平移后的 logp 对齐（位置 t 的 logits 预测 t+1），这里曾出过
`578 vs 579` 的形状错误。

### 4.4 评测协议

- **Spider**：dev300 分层抽样，`rows` 口径（行数一致 + 行列排序 + 数值归一化）；
- **BIRD**：**官方 set 口径**（原始元组、列序敏感、忽略行序与重复行）；
  单轮主数字跑**全量 dev 1534 条**（±1.3pp），三轮与三代数据对照跑**等距 307 条**
  （`stride 5`，同一批样本，三轮要 3 倍机时）；
- **单轮 / 三轮**：同一套 `SqlAgent`，`max_turns=1` 与 `3`；三轮用
  `--until-correct`（判对才停）测上限，否则执行成功就停会让三轮退化成单轮；
- **所有对照都在同一批样本上做**（配对比较），因为不同抽样的方差远大于效应量。

## 5. 结果

### 5.1 P2：DeepSeek 基线（判断任务是否成立）

| 设置 | EA | 执行失败 | 结果不符 |
|---|---|---|---|
| B1 单轮零样本 | **84.33%**（253/300） | 10 | 47 |
| B2 三轮判对才停 | **89.00%**（267/300） | 10 | 33 |
| 差值 | **+4.67pp** | 0 | −14 |

分难度：hard 74% → 83%（+9pp），extra 84% → 84%（0pp）。
**多轮增益集中在 hard**（聚合口径/JOIN 条件，反馈能定位）；extra 是"一开始就想错了"，
执行反馈救不了——这个模式在后来 P4/P6 反复出现。

### 5.2 P4：4B-SFT 第一次真训练

| 设置 | EA | easy | medium | hard | extra | 执行失败 |
|---|---|---|---|---|---|---|
| 4B-SFT 单轮 | **78.00%** | 88% | 84% | 66% | 57% | 19 |
| 4B-SFT 三轮 | **87.00%** | 92% | 89% | 83% | 78% | 15 |
| 增益 | **+9.00pp** | +4 | +5 | **+17** | **+21** | −4 |

- 4B 的多轮增益（+9.0pp）比 DeepSeek（+4.67pp）**更大**：它的错误更多是"聚合口径/JOIN"
  这类反馈能定位的问题，而 DeepSeek 剩下的错多是语义理解；
- 三轮 87.0% 已逼近 DeepSeek 的 89.0%；
- SFT：336 步 / 17.5 min / val_loss 0.0728（train 0.037）/ 显存 12.18G。

### 5.3 P5：outcome-only GRPO 在 Spider 上信号极弱

四次尝试，目标都是把零方差压下去：

| # | 设置 | 有梯度步数 |
|---|---|---|
| 1 | 三轮，全量 1500 prompt，G=4 | 10% |
| 2 | 三轮，hard/extra 396，轮级塑形（每多一轮 −0.1） | 26% |
| 3 | 三轮，库级留出 342 条 | 12% |
| 4 | 单轮，库级留出，T=1.0 | 13~19% |

**两次"想靠奖励设计救信号"的失败，值得单独记**：

1. **pass-rate 校准筛完只剩 2 条**：校准的 40 条里 p 均值 **0.90**（中位数 1.00）、
   35 条全对、3 条全错，只有 **2 条（5%）**落在 `0.2 < p < 0.8`；按 G=4 估算零方差 **0.96**，
   筛选后的训练集只剩 2 条。这条路被数据量直接堵死，所以最后没有走"校准 + 小样本"，
   而是换数据；
2. **轮级塑形没有降低轮数**：加"每多一轮 −0.1"之后，100 步里 `reward_mean` 稳定在 0.802，
   但平均轮数从 **1.65 升到 1.85**——正确率值 1、轮数只罚 0.1，模型学会了"用更多轮换更多的对"。
   这是奖励塑形被主奖励买走的典型例子，比"零方差 26%"更能解释为什么塑形没用。

（这两条的数据来自当时的 `metrics.jsonl`；临时实例已释放，产物未入库，故只作定性记录。）

最终（库级切分 + 单轮）：

| 设置 | t1 EA | t3 EA |
|---|---|---|
| SFT（110 库，留出 30） | 75.33% | 83.67% |
| GRPO seed 7 | **78.33%** | 85.33% |
| GRPO seed 8 | **76.33%** | — |
| 相对 SFT-110 | **+2.00pp（均值）** | +1.66pp |

n=300、SE≈2.4pp，+2.0pp 只有 0.8σ。**根因是每题成败近乎确定**：同一题 4 条轨迹
要么全对要么全错，不是奖励或学习率的问题。

### 5.4 P6：换 BIRD

#### 5.4.1 信号变好了

| 指标 | BIRD | Spider（P5） |
|---|---|---|
| `zero_var_ratio` | **0.615** | 0.74~0.90 |
| 有梯度步数 | **38.5%**（77/200） | 13~26% |
| `reward_mean` | 0.540 | 0.81~0.95 |
| 全对步数 / 全错步数 | 67 / 56 | — |

#### 5.4.2 但 200 步 outcome-only 没提升

| 设置 | EA（307 条，官方口径） |
|---|---|
| BIRD-SFT（490 步） | 50.16% (154/307) |
| + GRPO 200 步 | **50.16%** (154/307) |
| 差值 | **±0.0pp** |

同一批样本上完全没动。配对比较（n=103 重叠）也是 55.3% → 55.3%。

#### 5.4.3 三轮自修复只救回 9 条

| 口径 | EA |
|---|---|
| 单轮 | 50.16% |
| 三轮 | 53.09% |
| 增益 | +2.93pp（只多对 9 条） |

**153 条单轮错的样本里只有 9 条（5.9%）被后续轮次救回来**。原因很直接：
SFT 数据是单轮的，模型**根本没见过反馈该怎么用**。这判定了 P6 的前置条件：
先有多轮行为，才谈得上轮级优势。

### 5.5 P6 三代数据与最终配置

| 设置（同批 307 条） | t1 | t3 | 多轮才救回 | t3 执行失败 |
|---|---|---|---|---|
| v1：schema 修复 1133 条 | 51.47% | 54.07% | 8（2.6%） | 19 |
| v2：+ 取值修复 795 条（未 mask） | 46.91% | 55.37% | 26（8.5%） | 24 |
| **v3：同数据 + mask 第一轮** | **51.79%** | **57.00%** | **16（5.2%）** | **13** |

v3 在两条轴上都最好：单轮回到 51.79%，三轮 **57.00%**（比 v1 +2.93pp、比 v2 +1.63pp），
执行失败 19 → 13。

**全量补测（P7，1534 条，¥2.5 / 65 min）**：v3 单轮 **50.85%（780/1534）**，
SE 1.28pp、95% CI [48.35, 53.35]；分难度 easy 58.8% / medium 39.2% / hard 37.2%；
执行失败 151 条（9.8%）。与 307 条子集（51.79%）比，**抽样偏乐观 0.94pp**；
两者在 307 条上**逐条判定完全一致（307/307）**，说明全量结果是同一模型的确定性重跑，
不是换了配置。

### 5.6 轮级优势 vs outcome-only（同等训练预算）

| 设置（120 步 / G=4 / 3 轮） | t1 | t3 | easy | medium | hard |
|---|---|---|---|---|---|
| 多轮 SFT（v1 基线） | 51.47% | 54.07% | 62% | 39% | 30% |
| + outcome-only（β=0） | 51.14% | — | 61.7% | 37.6% | 34.8% |
| **+ 轮级优势（β=1）** | **52.77%** | **56.03%** | 63.4% | 38.5% | **39.1%** |
| 轮级 − outcome-only | **+1.63pp** | — | +1.7 | +0.9 | **+4.3** |
| 轮级 − SFT | +1.30pp | +1.96pp | +1.4 | −0.5 | **+9.1** |

训练侧机制证据（120 步）：`turn_adv_nonzero` 在 **71/120 步（59%）** 非零、
`zero_var_ratio` 0.60、`turns_mean` 1.90、`mask_mismatch` 恒 0、显存峰值 11.7G。

**方向对，但不显著**（见 §6.5）。轮级优势是唯一跑赢 SFT 基线的配置，增益集中在 hard
（+9.1pp），与"轮级优势对多次尝试的难题才有用"的机制一致。

## 6. 机制分析

### 6.1 零方差不能用均值准确率预测

BIRD 可行性阶段曾用二项分布估算：p=0.5、G=4 时全对概率 `p⁴`、全错 `(1−p)⁴`，
两者之和 = 0.125。**实测 0.615，差 5 倍。**

原因：那个公式假设"每道题成功率都一样"，而真实分布是**双峰**的——
67 步是"4 条全对"（SFT 已稳的题），56 步是"4 条全错"（4B 根本够不着的题），
均值 0.54 只是两头的加权平均。真正可学的只有中间 77 步（38.5%）。

**教训**：`zero_var_ratio` 必须实测；用均值算出来的"信号量"会高估 5 倍，
据此排训练预算会全部落空。

### 6.2 双峰难度决定了哪一半能被救

- **全对步**（67）：outcome 优势为 0，但轮级优势可以在这里制造信号
  （"一轮解出" vs "三轮才解出"）——这是轮级优势**唯一**能起作用的地方；
- **全错步**（56）：轮级也救不了（y 全 0），只能靠外部信息（更好的反馈、更大的模型）；
- **中间步**（77）：outcome 本来就有信号。

这解释了为什么轮级优势的增益集中在 hard（39.1% vs 30%）：hard 是"有时能做对、
但不是一次就对"的题，过程分化最大。

### 6.3 反馈的信息量是自修复的上限

三条独立证据指向同一结论：

1. **执行反馈本身的覆盖面**：BIRD 首轮错题里 79%~90% 是"能执行但结果错"
   （307 条：117/149；74 条抽样：26/29），执行报错只占 10%~21%；
   **P3 的 490 条"跑满 3 轮仍错"里，97%（474/490）属于这一类**——越往后剩下的，
   越是反馈看不见的错；
2. **P6 方案②**：让 DeepSeek 改 4B 的真实错误，成功率仅 **10%**——反馈里没有信息，
   强模型也改不动；
3. **P6 v1 → v3**：加上值检查（能检测"值拼错"这一类）后，多轮才救回
   2.6% → **5.2%**，三轮 +2.93pp。

也就是说：**可被反馈救回的错题比例，大致等于"反馈能检测到的错误"在这批错题中的占比**。
这不是 RL 能突破的——RL 只能让模型更好地利用已有信息。

### 6.4 "先写错再改"是病，不是能力

v2 的修复率 8.5%（v1 的 3.25 倍）看起来很好，代价却是单轮掉 4.6pp（51.47 → 46.91）。
原因是 49% 的样本里"故意写错的第一轮"也被算进了 loss——模型学会了
"先随手写一个、等反馈再改"。

v3 给修复样本加 `meta.mask_first_turn=True`，只对最后一轮算 loss
（多轮样本 loss token 115 → 57）。结果：

- 单轮回到 51.79%（比 v1 还高 0.3pp）；
- 三轮 57.00%（比 v1 +2.93pp）；
- 修复率回落到 5.2%，但**净收益更大**。

**这条是工程上最容易踩的坑**：多轮 SFT 数据如果不 mask 中间错误轮，
等于在教模型"错误是可以先写出来的"，而推理时没有第二次机会（单轮）。

### 6.5 统计功效：为什么"不显著"是如实结论

同一批 307 条样本上的配对比较（McNemar 精确检验）：

| 对比 | 差值 | 配对 SE | z | 精确 p | 95% CI |
|---|---|---|---|---|---|
| v3 t3 − v1 t3 | +2.93pp | 2.37pp | 1.24 | 0.272 | [−1.72, +7.58] |
| 轮级 − outcome-only（t1） | +1.63pp | 0.98pp | 1.67 | 0.180 | [−0.29, +3.54] |
| 轮级 − SFT（t1） | +1.30pp | 1.03pp | 1.26 | 0.344 | [−0.72, +3.32] |
| v3 t3 − v3 t1（多轮本身） | **+5.21pp** | 1.30pp | **4.00** | **<0.001** | [+2.66, +7.77] |

两条重要的自我修正：

1. 早前的记录写"+2.93pp ≈ 0.7σ"，那是按**独立样本** SE=4.0pp 算的。同一批题做配对比较
   时 SE 只有 2.37pp，z=1.24（p=0.27）。**配对检验更准，结论仍然不显著，但强度不同**；
2. 按当前效应量，要到 p<0.05 约需 **770 条**，要有 80% 功效约需 **1560 条**。
   n=307 的 +2.93pp 本就在噪声带里，继续加 seed 的成本/收益也不划算。

**唯一显著的是"多轮比单轮好"（+5.21pp，p<0.001）**——这是本项目最稳的结论。

## 7. 负结果与教训

### 7.1 outcome-only 在饱和任务上无效（P4/P5/P6）

Spider 上零方差 0.90 → 四次尝试最低只到 0.74；BIRD 上零方差降到 0.615 后，
200 步仍然 ±0.0pp。**换数据把信号量翻了 2~3 倍，但更新次数仍然不够**
（200 步 × 4 条 × 38.5% ≈ 308 条有效轨迹）。

### 7.2 "让强模型改 4B 的错"这条路不通（P3/P6）

修复成功率 10%。根因不是教师不行，是**反馈里没有信息**：首轮错题 79%~90% 是
"跑得对但结果错"，教师看到的只有 `1 row`。这直接推导出"要提升修复率，
必须先提升可检测性"（→ 值检查）。

### 7.3 多轮数据不 mask 第一轮会毁掉单轮能力（P6 v2）

见 §6.4。这是"数据构造"层面的坑，不是训练框架的问题。

### 7.4 轮级优势收益有限的三层原因（P6 §7.10）

1. **任务层**：BIRD 首轮错题的 79%~90% 是"执行成功但结果错"，执行反馈不携带纠错信息；
2. **数据层**：1133 条修复只覆盖"列名不存在"，覆盖不到语义错误（v2 补了 795 条取值修复）；
3. **统计层**：307 条样本、单 seed，1~3pp 的效应需要约 770~1560 条才能显著。

### 7.5 工程坑（都会静默毁掉实验）

| 坑 | 现象 | 修法 |
|---|---|---|
| KL 参考策略是基座 | `kl` 1.7~2.6，每步拉回未 SFT | `kl_beta=0` |
| `use_cache=False` 被继承 | 生成慢 5 倍、OOM | 显式 `use_cache=True` |
| 更新时停在 `eval()` | 梯度检查点不生效 → OOM | `model.train()`，检查点在 peft 包装前开 |
| 逐 token 优势形状 | `578 vs 579` | `adv[:, 1:]` 与平移 logp 对齐 |
| 结果截断造成假阳性 | 两个不同 SQL 被判等价 | `--max-rows 20000` |
| BIRD 列名带空格 | 模型自己删空格 → 语法错 | prompt 里加双引号 |
| `nohup` 日志"卡住" | stdout 块缓冲，8KB 才落盘 | 看 `metrics.jsonl`（每步关文件） |
| 轮级优势脚本 ImportError | `fill_turn_advantages` 忘了 import | 训练脚本的 import 不在单测覆盖范围内，上卡前先 `--steps 1` 冒烟 |

## 8. 局限与下一步

### 局限

1. **样本量**：BIRD 的**对照结果**仍是 n=307、单 seed（单轮主数字已补全量 1534）；
   +2.93pp 的配对 p=0.27，不声称显著；
2. **口径**：`rows` 口径偏宽松，非官方 test-suite；BIRD 为官方 `set` 口径的再实现，
   与官方脚本在超时/类型处理上有细微差别；
3. **未做**：Spider test200、多 seed、官方 test-suite 复核；
4. **模型规模**：4B 的天花板明显（BIRD 零样本 49.8%），结论是机制层面的相对趋势，
   不是 SOTA 对比。

### 下一步（按优先级）

1. **跨查询自洽检查**：现在只有"值存在性"一种语义检查。可以做
   "同一问题的多条 SQL 结果是否一致"、"聚合列是否在 group 内"等更结构化的检查——
   这是继续提升修复率的关键，而不是加训练步数；
2. **三轮全量**（1534 条，约 3.2h / ¥8）：把 t3 的 ±2.9pp 也压到 ±1.3pp；
   现在 t1 已经是全量，只有 t3 还是 307 条；
3. **困难子集 + pass-rate 校准**：把"67 步全对"和"56 步全错"筛掉，只留 `0.2 < p < 0.8`，
   在同样步数下把有效轨迹翻倍；
4. （不推荐）多 seed 追显著性：3 seeds 约 ¥8 / 3.2h，而 std 大概率仍覆盖 0。
